# Phase 01.1: cookie-auth-and-recovery — Context

**Gathered:** 2026-05-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 01.1 delivers **persistent auth across iOS PWA restarts** — the specific bug where iOS Safari's ITP evicts `localStorage` on PWA force-quit → reopen, forcing users back through onboarding and losing their session.

Three deliverables:
1. **Cookie migration:** Move `auth_token` storage from `localStorage` to an HttpOnly same-origin cookie, set via Next.js rewrites that proxy `/api/*` → Railway. The browser handles cookie delivery automatically; `lib/api.ts` and `lib/ws.ts` require no token-handling code.
2. **Idempotent rejoin:** `POST /households/join` silently returns the existing member's token if a member with the same name (case-insensitive) already exists in the household. Covers the edge case where even the cookie is gone (device wipe, new phone).
3. **Settings screen:** New `/settings` route showing household invite code (copyable) + current member's name and color dot — read-only display, no editing.

**Not in this phase:** Supabase Auth, OAuth, token rotation, member name/color editing, leave-household flow, export from settings.

</domain>

<decisions>
## Implementation Decisions

### Cookie delivery mechanism

- **D-01:** Add `rewrites` to `frontend/next.config.ts` proxying `/api/:path*` → `${process.env.RAILWAY_URL}/:path*`. This makes all API calls (including WebSocket upgrades) same-origin from the browser's perspective. Railway's `Set-Cookie` response header passes through Vercel transparently and is set on the Vercel origin. `NEXT_PUBLIC_API_BASE` becomes an empty string (all calls use `/api/...` paths). `NEXT_PUBLIC_WS_BASE` similarly becomes empty; the WS URL becomes `/ws` (relative to Vercel origin).

  The rewrite also proxies WebSocket connections (`wss://vercel.app/ws` → Railway). Next.js rewrites support WS protocol upgrades natively.

### Cookie attributes

- **D-02:** Cookie name: `aldente_auth`. Attributes: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, `Max-Age=7776000` (90 days). Backend refreshes the `Max-Age` on every authenticated response so an active user never expires. Railway must set these attributes explicitly — do not rely on Vercel to add them.

### Bearer header fallback (dual-mode)

- **D-03:** Backend `auth.py` accepts BOTH the `aldente_auth` cookie AND the `Authorization: Bearer` header. Cookie is checked first; Bearer header is the fallback. This preserves local dev with `curl`/Postman, preserves existing sessions during rollout, and keeps Phase 1's backend tests valid. No expiry on the Bearer path in v0.1.

### api.ts simplification

- **D-04:** `lib/api.ts` drops the manual `Authorization: Bearer` header injection entirely. `fetch()` calls are relative (`/api/...`); the browser sends the `aldente_auth` cookie automatically. The `401` handler still wipes any residual localStorage entries (backward-compat cleanup) and redirects to `/onboarding/welcome`. `NEXT_PUBLIC_API_BASE` defaults to `""` in production (set the env var to `""` in Vercel); for local dev without Railway, it can still point to `localhost:8000`.

### WebSocket auth

- **D-05:** `lib/ws.ts`'s `createRealtimeClient(token)` signature changes to `createRealtimeClient()` — no token parameter. The WS URL becomes `${location.origin.replace('https://', 'wss://')}/ws` (or just `/ws` constructed from `window.location`). The browser includes `aldente_auth` cookie on the same-origin WS upgrade request automatically. The backend `routers/ws.py` reads the token from the `Cookie` header on upgrade, falling back to the existing `?token=` query-string path (dual-mode, same as D-03). On `1008` close, `ws.ts` removes the cookie (via a `DELETE /api/auth/session` endpoint or document.cookie clear — planner decides) and redirects to onboarding.

### Client-side identity (household_id, member_id)

- **D-06:** `localStorage` keys `household_id` and `member_id` are removed. On app mount, `RealtimeProvider` (or a new `SessionProvider`) calls `GET /households/me` — the `aldente_auth` cookie is auto-attached. The response provides `household_id`, `member_id`, `name`, `color_hex`, `invite_code`, and the full member roster. This data is held in React context for the app lifetime. The onboarding guard's `hasOnboarded()` becomes a server-side check (cookie present = onboarded); if `GET /households/me` returns 401, redirect to onboarding.

### Idempotent rejoin

- **D-07:** `POST /households/join` checks for an existing member with a matching name (case-insensitive, trimmed) BEFORE attempting to create a new row. If found: return the existing member's `auth_token` and IDs in the same `OnboardingResponse` shape — no new row inserted. If the name is not found: create new member as before (color uniqueness check still applies). The response body and `Set-Cookie` header are identical regardless of whether the member was found or created.

  Matching criterion: name only (case-insensitive). Color in the request body is ignored for the lookup — users may have forgotten which color they originally picked.

### Settings screen

- **D-08:** New route `frontend/app/settings/page.tsx` (accessible from bottom nav or similar). Contents (read-only):
  - Household invite code — displayed large, with a native `navigator.clipboard.writeText()` copy button
  - Current member's name and color dot
  - Household name

  No editing, no delete/leave in Phase 01.1. The settings icon in the bottom nav (or a gear icon on the home page) navigates here. Planner decides exact nav placement.

### Claude's Discretion

The following are implementation details the planner and executor should decide without re-asking:

- **`RAILWAY_URL` env var naming:** Use `RAILWAY_URL` server-side (not `NEXT_PUBLIC_`) since it's only read in `next.config.ts` at build/request time — never exposed to the browser bundle.
- **Cookie clear on logout/1008:** Clearing an HttpOnly cookie from JS isn't possible directly. Add `DELETE /api/auth/session` that returns `Set-Cookie: aldente_auth=; Max-Age=0` to clear server-side. Or add a Next.js API route at `app/api/auth/session/route.ts` for this purpose (since `next.config.ts` rewrites can't delete cookies on behalf of JS).
- **`lib/auth.ts` migration:** Remove `saveAuthToken`, `getAuthToken`, `clearAuth`, `hasOnboarded` exports or replace with no-op stubs until all callers are updated. `AUTH_TOKEN_CHANGED_EVENT` may still be useful for triggering a `GET /households/me` refresh — keep if `RealtimeProvider` uses it.
- **Alembic migration:** Not required for this phase — the schema doesn't change. Cookie auth is purely a transport-layer change.
- **`onboarding-guard.tsx` replacement:** The `hasOnboarded()` check moves from localStorage read to: "does `GET /households/me` return 200?" The guard may become a server component or rely on a `SessionProvider` context. Planner decides.
- **Local dev:** Developers can set `RAILWAY_URL=http://localhost:8000` in `.env.local` and `next.config.ts` rewrites will proxy to the local backend. No cookie-domain issues because both run on `localhost`. The Bearer fallback (D-03) means existing `curl`-based dev flows still work.
- **CORS:** Since API calls are now same-origin (via rewrite), the backend CORS allowlist no longer needs to include the Vercel frontend domain for API routes. Keep `localhost:3000` for any direct-to-Railway dev workflow. Planner should note whether to trim the CORS allowlist.

</decisions>
