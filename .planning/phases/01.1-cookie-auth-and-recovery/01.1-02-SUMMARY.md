# Phase 01.1 Plan 02: Idempotent Rejoin Summary

**One-liner:** `POST /households/join` now returns existing member's token on name-match (case-insensitive, trimmed) before attempting any insert — device-wipe recovery works even without a cookie.

## What Was Built

### Match algorithm

`join_household` in `backend/app/routers/households.py` now has a three-stage flow:

1. **Household lookup** — 404 if invite_code unknown (unchanged)
2. **Name-match check (new)** — `func.lower(Member.name) == body.member_name.strip().lower()` against all members in the household. If found: emit Set-Cookie with the existing token and return the existing member's IDs. No new row inserted, no `db.commit()`.
3. **Color-uniqueness check** — 409 if color taken (unchanged, only reached when no name match)
4. **New member insert** — create row with `name=body.member_name.strip()` (trimmed before storage)

### Where the rejoin branch sits

```
join_household()
  ├── household lookup → 404 if not found
  ├── [NEW] normalized_name = body.member_name.strip().lower()
  ├── [NEW] existing_member = db.scalar(... func.lower(Member.name) == normalized_name ...)
  ├── [NEW] if existing_member: set_auth_cookie + return existing IDs  ← rejoin path
  ├── color uniqueness check → 409 if taken
  └── new Member insert → set_auth_cookie + return new IDs
```

### Color is ignored on the rejoin branch

The request body's `color_hex` is not read on the rejoin branch. Users who forgot their original color can rejoin without knowing it. The color they provide is silently ignored.

### Cookie on both branches

`set_auth_cookie(response, ...)` is called on both the rejoin path (`existing_member.auth_token`) and the new-member path (`member.auth_token`). The response shape (`OnboardingResponse`) is identical in both cases.
