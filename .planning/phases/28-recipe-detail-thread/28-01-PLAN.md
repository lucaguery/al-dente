       ```python
       def _apply_put_pinning(
           db: Session,
           recipe: Recipe,
           body: RecipeUpdate,
           pre_update_snapshot: dict,
       ) -> None:
           """Phase 28 DETAIL-05 — diff-based auto-pin on PUT /recipes/{id}.

           Compares the PUT body's AnswerField keys against `pre_update_snapshot`
           (taken BEFORE the setattr loop). Differing values pin the field; values
           that arrive blank (per `_is_blank_for_field`) UNPIN the field. Same-value
           re-saves are a no-op (D-08).

           Runs BEFORE the setattr loop so the diff sees the OLD values — calling
           after setattr would mean getattr(recipe, field) already holds the new
           value and the diff would be empty (28-RESEARCH.md §2 enum-coercion
           ordering gotcha).

           Mirrors the same set-semantics + sorted reassignment idiom as
           `_apply_answer_turn` and `_apply_proposal_accepted`. Same DB transaction
           as the field writes (invariant #3).
           """
           data = body.model_dump(exclude_unset=True)
           current_pins: set[str] = set(recipe.manually_edited_fields or [])

           for field_name, new_value in data.items():
               if field_name not in _ANSWER_FIELD_SET:
                   continue  # D-10: only AnswerField keys eligible

               old_value = pre_update_snapshot.get(field_name)

               # Coerce new_value to a comparable shape matching how the setattr
               # loop will store it. Order-insensitive comparison for list-of-enum
               # fields (mood, seasonality) — D-09 / 28-RESEARCH.md §2 list-order
               # gotcha.
               if field_name in ("cuisine", "main_protein") and new_value is not None:
                   coerced_new = _coerce_enum_value(new_value)
               elif field_name in ("mood", "seasonality") and new_value is not None:
                   coerced_new = sorted([_coerce_enum_value(v) for v in new_value])
                   old_value = sorted(list(old_value or []))
               elif field_name == "ingredients" and new_value is not None:
                   coerced_new = [
                       (i.model_dump() if hasattr(i, "model_dump") else i)
                       for i in new_value
                   ]
               else:
                   coerced_new = new_value

               if _is_blank_for_field(field_name, coerced_new):
                   # D-09 — clearing UNPINS
                   current_pins.discard(field_name)
                   continue

               if coerced_new != old_value:
                   # D-08 — same value is a no-op; differing value pins
                   current_pins.add(field_name)

           recipe.manually_edited_fields = sorted(current_pins)
       ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → PUT /api/recipes/{id} | Untrusted body; passes through Pydantic `RecipeUpdate` validation. `_UPDATE_FORBIDDEN_FIELDS` strips disallowed keys defense-in-depth. |
| client → manually_edited_fields | Client CANNOT directly set this column — defense-in-depth via `_UPDATE_FORBIDDEN_FIELDS`. Only `_apply_put_pinning`, `_apply_answer_turn`, `_apply_proposal_accepted` mutate it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-02 | Tampering | `_apply_put_pinning` race with concurrent answer-turn POSTs | accept | Backend invariant #7 (single uvicorn worker, single asyncio event loop) serializes coroutine execution. Per-recipe ordering is established by Phase 26's `acquire_position_lock` on the turn-write path. PUT does not need an additional lock because: (a) FastAPI serializes per-request handler invocations on the single worker; (b) both PUT and answer-turn POST use `db.commit()` so PostgreSQL row-level locking provides last-write-wins on `manually_edited_fields` — and the field is sorted/set-based, so partial overlaps converge to the union of pinned fields. Productize-later (Railway scale-out): swap to `SELECT FOR UPDATE` on `recipes.id` if multi-worker arrives. |
| T-28-05 | Tampering | Client passes `manually_edited_fields` in PUT body to skip diff and force a custom pin set | mitigate | `_UPDATE_FORBIDDEN_FIELDS` strips this key BEFORE setattr (line 360 `if key in _UPDATE_FORBIDDEN_FIELDS: continue`). Confirmed kept unchanged in this plan. Test surface: any T-28 case sending `manually_edited_fields` in the body must show the column unchanged by the body (only by the diff). |
| T-28-06 | Information Disclosure | The `recipe.updated` broadcast leaks `manually_edited_fields` to all household members | accept | Pin set is not sensitive — both household members are co-equal editors per the v0.6 design. Cross-household isolation already enforced at the broadcast level via `broadcast_to_household(member.household_id, ...)`. |
