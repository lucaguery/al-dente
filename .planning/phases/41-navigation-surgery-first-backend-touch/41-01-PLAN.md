<objective>
Add the `DELETE /votes/{vote_id}` backend endpoint with full 5-test contract, extend POST to return the new `vote_id` (and include it in the existing `vote.created` broadcast), and add the `vote.deleted` realtime event. This is the entire backend slice for UNDO-01 — the frontend deck-undo plan (41-04) depends on this contract.

Purpose: Per architecture invariant #2, voting state is COMPUTED from rows — never stored. Undo therefore must DELETE the row, not flip a stored state. This plan is the canonical implementation of that DELETE path plus the regression test that the planner-level rule (no `state` column) holds against this code change. The 409-on-veto-window-closed branch is defense-in-depth for the frontend's preemptive tooltip (D-12); the deck button is disabled when veto window closes, so this branch should fire only on a race between page load and undo tap.

Output: One new route handler, one extended response shape, one new broadcast event, six new pytest cases, and one invariant-regression test. No DB schema changes — voting state stays computed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → DELETE /votes/{vote_id} | Authenticated HTTP request; vote_id is path param (untrusted) |
| Member.household_id → cross-household join | Internal DB join; verifies the targeted vote belongs to the auth'd member's household |
| broadcast_to_household → WebSocket fanout | Outbound broadcast to all sockets registered for the household_id; payload is server-controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-41-01 | Information Disclosure | DELETE /votes/{vote_id} cross-household | mitigate | Return 404 (not 403) on missing-OR-wrong-household — both branches return identical status + body so an attacker cannot distinguish "vote does not exist" from "vote belongs to another household" (invariant #2 record-existence non-leak). Tested via test_delete_vote_404_cross_household. |
| T-41-02 | Tampering | DELETE bypass via direct DB | accept | Attacker with DB access can delete any vote — out of scope for HTTP endpoint design. Supabase RLS productize-later. |
| T-41-03 | Tampering | Race: undo after partner marks cuisiné | mitigate | 409 veto_window_closed gate fires on CookingLog existence for `(household_id, shortlist_date)`. Tested via test_delete_vote_409_veto_window_closed. Frontend preemptive tooltip (Plan 41-04) is the primary UX; backend 409 is defense-in-depth (D-12). |
| T-41-04 | Repudiation | "I didn't undo that vote" | accept | Vote rows are hard-deleted (per invariant #2 — state is computed). No audit trail kept for couple-scale MVP. The vote.deleted broadcast goes to both household members, so partner sees the undo in real time — that's the social audit trail. Productize-later: append-only votes_history table. |
| T-41-05 | Denial of Service | Unauthenticated DELETE flood | mitigate | `Depends(current_member)` returns 401 before the handler body runs — no DB query for unauthenticated traffic. |
| T-41-06 | Elevation of Privilege | Spoof another member's vote deletion | mitigate | The handler uses `member.household_id` from `current_member` (cookie-derived) for the isolation check — never from path params or body. Tested via test_delete_vote_404_cross_household. |
</threat_model>
