<objective>
Build the active cooking session route — `frontend/app/cooking-logs/[id]/active/page.tsx` — that lets the user step through a recipe's structured `steps[]` with progress segments, ingredient cross-refs, and a single tap to the existing `/cooking-logs/[id]/finalize` page when the last step is reached.

This plan owns the entire front-end surface for ACTV-01 (route shell + det-top + progress segments), ACTV-02 (step navigator + backfill loading state), and ACTV-03 (finalize CTA wiring). It also owns the TypeScript type update (`Recipe.steps: StepEntry[]`) to match the new backend contract, the `triggerStepsExtraction` API helper, and the `cooking.active.*` i18n namespace.

Two surprises from 42-RESEARCH.md need explicit handling:

- **R-02** — `cooking_logs.cooked_at`, NOT `started_at`. CONTEXT.md D-15 referred to `started_at`; the actual TS type field is `cooked_at`. The elapsed-time computation reads `cookingLog.cooked_at`.
- **R-03/R-04** — `Recipe.steps` shape change is breaking. Plan owns the TS type update. The runtime detection helper handles three states: empty (length===0), legacy (entries are strings), structured (entries are StepEntry-shaped objects). Empty + legacy both route to the loader + backfill trigger; structured routes to the navigator.

The page subscribes directly to `recipe.updated` via `useRealtime().onEvent` — `RealtimeProvider` does NOT currently re-fire `recipe.updated` as a DOM CustomEvent (only `recipe.promoted` triggers a toast there), so the subscription is local to /active. When the BackgroundTask from plan 42-03 commits and broadcasts, the local recipe state updates and the UI flips from loader to step 1.
</objective>
