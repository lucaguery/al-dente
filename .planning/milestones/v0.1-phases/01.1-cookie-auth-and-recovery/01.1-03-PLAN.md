<objective>
Configure Next.js rewrites so `/api/*` HTTP calls and `/ws` WebSocket upgrades from the browser appear same-origin (Vercel) but transparently proxy to Railway. This is the foundation that makes HttpOnly cookies work — a same-origin cookie set by Railway on the Vercel origin survives because browsers treat the rewrite as a same-origin response.

Purpose: Without same-origin rewrites, the `aldente_auth` cookie set by Railway would be on a third-party domain (`api.aldente.example`) and iOS Safari ITP would clamp it. Same-origin via rewrites is the single architectural change that makes cookies viable on iOS PWA.

Output: `next.config.ts` with a `rewrites()` config; `.env.example` documenting `RAILWAY_URL`; an optional Next.js API route at `app/api/auth/session/route.ts` that forwards DELETE to Railway (defense in depth — if for some reason the rewrite path needs a server-component-callable variant, this exists).
</objective>

```typescript
import { NextResponse } from "next/server";

// Same-origin DELETE /api/auth/session forwarder.
// Forwards to backend's DELETE /auth/session and passes through the
// Set-Cookie header so the aldente_auth cookie clears on this origin.
export async function DELETE(request: Request) {
  const railway = process.env.RAILWAY_URL;
  if (!railway) {
    return NextResponse.json({ error: "RAILWAY_URL not set" }, { status: 500 });
  }
  const upstream = await fetch(`${railway.replace(/\/+$/, "")}/auth/session`, {
    method: "DELETE",
    headers: { cookie: request.headers.get("cookie") ?? "" },
  });
  const res = NextResponse.json(await upstream.json().catch(() => ({ ok: true })), {
    status: upstream.status,
  });
  const setCookie = upstream.headers.get("set-cookie");
  if (setCookie) res.headers.set("set-cookie", setCookie);
  return res;
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vercel rewrites layer → Railway | Vercel terminates TLS, then forwards to Railway. The rewrite is server-to-server, untrusted user input passes through. |
| Browser → Vercel origin (same-origin from cookie's POV) | The whole point of this plan: collapse cross-origin to same-origin. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01.1-03-01 | Information Disclosure | RAILWAY_URL accidentally exposed in browser bundle | mitigate | Use `RAILWAY_URL` (NOT `NEXT_PUBLIC_RAILWAY_URL`). Next.js only inlines NEXT_PUBLIC_ vars into the browser bundle; server-side env vars used in next.config.ts run at build/request time on the server only. Verified by Next.js docs §"Loading Environment Variables". |
| T-01.1-03-02 | Spoofing | Open redirect via rewrite path | mitigate | `source: "/api/:path*"` is a fixed prefix; the destination is a fixed `${RAILWAY_BASE}/:path*` template. There is no user-controlled redirect target. |
| T-01.1-03-03 | DoS | Misconfigured RAILWAY_URL silently breaks all auth | mitigate | Build-time `throw new Error` guard fails the Vercel deploy if RAILWAY_URL is missing — louder than a runtime 502 cascade. |
| T-01.1-03-04 | Tampering | Rewrites strip security headers | accept | Next.js rewrites preserve response headers including Set-Cookie by default. Tested by Plan 06 manual smoke (cookie persists in browser DevTools after onboarding). |
| T-01.1-03-05 | Information Disclosure | WS upgrade leaks cookie cross-tab | accept | SameSite=Strict (Plan 01 D-02) blocks cross-site sends; same-origin tabs intentionally share cookies — that's the feature. |
