<objective>
Make `POST /households/join` idempotent on member name. If the household already has a member whose name (case-insensitive, trimmed) matches the request, silently return that member's existing token + IDs instead of trying to insert a duplicate row. Covers the device-wipe / new-phone edge case where even the cookie is gone — the user re-runs onboarding with the same name and is reunited with their original member identity.

Purpose: Without this, a user whose cookie is gone (cleared cache, new phone, factory reset) and whose name+color collide with their previous self gets a 409 and can't recover. The invite code isn't enough either — the second member would create a new row, orphaning their old votes/cooking_logs.

Output: `join_household` checks for an existing matching member BEFORE the color-uniqueness check. Match criterion: `name` only (case-insensitive, whitespace-trimmed). Color in the request body is ignored on the rejoin branch — users may have forgotten which color they originally picked.
</objective>

```python
    household = db.scalar(
        select(Household).where(Household.invite_code == body.invite_code)
    )
    if household is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="invite_code not found",
        )

    # D-07: idempotent rejoin. Match on name only (case-insensitive, trimmed).
    # If a member already exists in this household with a matching name,
    # silently return their existing token + IDs. Color in the body is
    # ignored on this branch — users may have forgotten which color they
    # originally picked.
    normalized_name = body.member_name.strip().lower()
    existing_member = db.scalar(
        select(Member).where(
            Member.household_id == household.id,
            func.lower(Member.name) == normalized_name,
        )
    )
    if existing_member is not None:
        set_auth_cookie(response, existing_member.auth_token)
        return OnboardingResponse(
            household_id=household.id,
            member_id=existing_member.id,
            auth_token=existing_member.auth_token,
            invite_code=household.invite_code,
        )

    # Net-new member path — color uniqueness still applies.
    existing_colors = set(
        db.scalars(
            select(Member.color_hex).where(Member.household_id == household.id)
        ).all()
    )
    if body.color_hex in existing_colors:
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail="color already taken by another member",
        )
    member = Member(
        household_id=household.id,
        name=body.member_name,
        color_hex=body.color_hex,
        auth_token=generate_auth_token(),
    )
    db.add(member)
    db.commit()
    db.refresh(member)
    set_auth_cookie(response, member.auth_token)
    return OnboardingResponse(
        household_id=household.id,
        member_id=member.id,
        auth_token=member.auth_token,
        invite_code=household.invite_code,
    )
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (untrusted) → POST /households/join | invite_code + member_name + color_hex are all attacker-controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01.1-02-01 | Spoofing | Idempotent rejoin via guessed name | mitigate | The 6-char invite_code is the credential — the attacker must possess it AND the victim's name to take over the session. SPEC.md treats invite_code as bearer-of-trust at couple-scale; the rejoin branch does not weaken this. The attacker who knows both is already in the trust circle. |
| T-01.1-02-02 | Spoofing | Case-insensitive name collision (e.g. "Luca" vs "lUcA") | accept | Intentional per D-07 — the whole point is that the user can recover with any casing of their name. Couple-scale, no impersonation pressure. |
| T-01.1-02-03 | Information Disclosure | Rejoin response leaks existing auth_token | mitigate | Only happens when the request includes a valid invite_code that grants access to the household anyway. No additional data is leaked beyond what `POST /households/join` already returns. |
| T-01.1-02-04 | DoS | Unbounded rejoin attempts on a known invite_code | accept | Couple-scale; rate-limiting deferred to productize-later (V2-AUTH-01). |
| T-01.1-02-05 | Elevation of Privilege | Idempotent rejoin replacing legitimate auth | mitigate | Rejoin returns the EXISTING token; no new token is minted. The attacker gains the same privileges as a successful HTTP request with that token, no more. |
| T-01.1-02-06 | Tampering | Concurrent rejoin race (two devices same household, same name, same time) | mitigate | Both reads see the same `existing_member` row and return the same token. Idempotency naturally serializes — no new row inserted, no constraint violation possible. |
</threat_model>
