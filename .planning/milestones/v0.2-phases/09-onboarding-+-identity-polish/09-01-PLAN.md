<interfaces>
<!-- Next.js 16 ImageResponse contract per training-drift docs (CRITICAL). -->
<!-- Source: frontend/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/app-icons.md -->

The `app/icon.tsx` and `app/apple-icon.tsx` files are file-convention routes.
Next.js 16 auto-discovers them and emits `/icon` and `/apple-icon` URLs
that the manifest and `<head>` resolution chain pick up.

Required exports:
```ts
import { ImageResponse } from "next/og";

export const size = { width: number, height: number };
export const contentType = "image/png";  // or "image/jpeg"

export default function Icon() {
  return new ImageResponse(
    (<div style={{ ... }}>...</div>),
    size,
  );
}
```

`next/og` is the Next.js 16 import (formerly `next/server` in older
versions — DO NOT use `next/server` here).

The runtime is the edge runtime by default. `ImageResponse` JSX accepts
inline `style` (no Tailwind classes — the runtime does not resolve CSS
tokens). Inline SVG is supported.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → static manifest.json | Browser fetches `/manifest.json` over HTTPS; values are static metadata (no untrusted input) |
| Browser → /icon, /apple-icon edge routes | Server-rendered ImageResponse; no user input enters the route handler |
| iOS Safari PWA install → on-device home-screen icon | OS-controlled chrome rendering; we control only the source PNG bytes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01-01 | Tampering | `frontend/public/manifest.json` | accept | Static asset; no user input. The migration changes only LITERAL hex values (`#C8553D`, `#FAF7F2`). Any tampering would require write access to the deployed bundle (Vercel-controlled) — out of scope for the application threat model. |
| T-09-01-02 | Information Disclosure | `frontend/app/icon.tsx`, `frontend/app/apple-icon.tsx` | accept | The ImageResponse handler reads no request data and renders only static SVG with hardcoded literal hex. No PII, no auth tokens, no household scoping. The route is intentionally public — install icons must be reachable without authentication. |
| T-09-01-03 | Spoofing (icon) | iOS home-screen icon rendering | accept | The icon visual is unauthenticated platform chrome; an attacker who can install a malicious PWA already controls more than the icon. The Slow-Food food-symbol on terracotta is identity-bearing but not an authentication factor. |
| T-09-01-04 | DoS via ImageResponse | `/icon`, `/apple-icon` edge routes | mitigate | Next.js 16 ImageResponse caches at the edge (build-time generation per the docs at `frontend/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/app-icons.md`). The handler executes once at build, not on every request. No dynamic input → no amplification vector. Verification: `npm run build` produces a static asset that subsequent requests serve from the CDN cache. |
| T-09-01-05 | XSS via SVG payload | `frontend/app/icon.tsx`, `frontend/app/apple-icon.tsx` | accept | SVG `<path d="...">` data is hardcoded literal in the source — no user input concatenation. ImageResponse renders to PNG (NOT served as raw SVG), so even hypothetical SVG-script vectors would be neutralized at the rasterization step. |
</threat_model>
